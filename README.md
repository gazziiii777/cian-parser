# cian-watch

Следит за выдачей Циана, пишет объявления и историю цен в Postgres, для каждого объявления
берёт рыночную оценку на price.domclick.ru и печатает в консоль новые объявления, изменения
цены и оценку рядом с ценой продавца.

## Как работает

Один процесс, один браузер, один прокси и три параллельные задачи, у каждой свой контекст
браузера с собственным отпечатком: лента новых (с ней же Домклик и аренда рядом), обход продажи
по районам, обход аренды по районам. Перезапуск браузера общий: задача, поймавшая капчу или
падение, перезапускает его (с ротацией IP, если задана), остальные видят новое поколение
браузера и переоткрывают свои контексты при следующем обращении.

**Лента новых**, каждые `CIAN_POLL_INTERVAL_SECONDS`:

1. Camoufox (Firefox с подменой отпечатка) один раз открывает URL выдачи: это даёт сессию,
   отпечаток и точный `jsonQuery` под фильтр (из JSON `window._cianConfig['frontend-serp']` в HTML).
2. Дальше страницы ленты берутся POST-запросами к `api.cian.ru/search-offers/v2/search-offers-desktop/`
   из той же вкладки, без рендера, страница за страницей до первой, где нет ни одного
   неизвестного объявления (потолок `CIAN_PAGES`). Обычно это 1–2 страницы, после простоя больше.
   Антибот Циана смотрит на отпечаток соединения, а не на куки: curl с куками браузера получает
   403, поэтому запросы идут именно из вкладки. На не-200 вкладка переоткрывает выдачу и повторяет.
3. Выдача сверяется с таблицей `offers` в одной транзакции: новые объявления вставляются,
   у известных обновляется `last_seen_at`, при смене цены пишется строка в `price_history`.
   Новые и подорожавшие/подешевевшие печатаются в консоль.
4. Объявления выдачи без строки в `domclick_estimates` оцениваются в Домклике (до 30 за опрос),
   оценка пишется в базу и печатается строкой `DOMCLICK` с расхождением цены продавца и рынка.
5. Для каждого нового объявления считается аренда похожих квартир: та же выдача Циана,
   но `flatrent`, те же комнаты, площадь ±20%, лесенкой: сам дом (если сдаётся 3+ похожих),
   квадрат около 1 км вокруг координат (полигон в `jsonQuery`, 5+ похожих), район. В базу
   и в сообщение идут медиана, размер выборки, охват и окупаемость (цена / годовая аренда).
   Когда в районе за 30 дней накопилось 3+ сданных, добавляется строка «сдано: N, медиана, дней».
6. Пауза `CIAN_POLL_INTERVAL_SECONDS` плюс случайный джиттер, и снова с шага 1.

**Районный обход**, две задачи (продажа и аренда), каждая идёт по районам непрерывно с паузой
`CIAN_SWEEP_PAUSE_SECONDS` между районами; район берётся снова не раньше, чем через
`CIAN_SWEEP_INTERVAL_MINUTES`:

- берутся районы, где есть активные объявления, и каждый читается целиком по тому же фильтру
  (все страницы, пока они полные): так каждое наше объявление попадает в кадр, пока живёт на сайте;
- цены обновляются, точки идут в `price_history`; любое изменение цены (📉 и 📈), снятие 🚫 и
  возвращение ↩️ уходят в Telegram только тем, кто нажал «Отслеживать» под этим объявлением,
  по остальным тишина;
- объявление, не попавшее в `CIAN_SWEEP_MISSES_TO_SELL` обхода своего района подряд, получает
  статус `sold` и `sold_at`, слежка за ним прекращается, строка остаётся. Появилось снова:
  статус возвращается в `active`. Циан не сообщает, продана ли квартира: `sold` значит
  «пропала с сайта», чаще всего это продажа;
- в тех же районах обходится вся долгосрочная аренда квартир (без фильтра по комнатам и площади):
  объявления аренды пишутся в `offers` с `deal_type = rent`, цены в историю, пропавшие получают
  статус `rented` и `sold_at`. Так копится история «что сдалось, почём и за сколько дней»;
  Telegram аренда не трогает.

Первый проход после каждого старта только пишет в базу, в Telegram ничего не уходит: так
перезапуск (деплой, падение) не выливается в пачку накопившихся объявлений. То же при пачке
новых больше 40 за проход (простой парсера). На 429 от Telegram бот ждёт `retry_after` и
повторяет отправку. Оценки Домклика берутся только для новых объявлений прохода
и для тех, что раньше ушли в Telegram без оценки, до 30 за проход.

**Фоновый досчёт.** Объявления, попавшие в базу без оценок (тихий проход, обход района),
досчитываются между проходами ленты пачками по 40: сначала Домклик, потом аренда рядом,
свежее увиденные первыми. Для аренды нужны координаты и этаж, их обходы районов дописывают
в `offers` (`lat`, `lng`, `floor`). Если похожих в аренду нет ни в доме, ни в 1 км, ни в районе,
в `rent_estimates` ложится строка с нулевой выборкой, и объявление больше не проверяется;
в списках по окупаемости такие не участвуют. Пока досчёт идёт, список «по окупаемости» в боте
растёт по ходу.

## Домклик

Сайт price.domclick.ru закрыт Qrator: без браузера API отвечает 401. Поэтому у Домклика свой
контекст в том же Camoufox, без прокси: один раз открывается главная оценки, после этого куки
контекста пускают в JSON API `price-bff.domclick.ru`, и оценка это два GET без кликов по форме:

1. `geo/suggest/?query=<адрес без «Россия, »>` даёт список домов с `guid`, берём первый.
2. `price/predict/?guid=&comm_sq=<площадь>&rooms=&floor=&quality=2` даёт рыночную цену,
   цену метра и диапазон (в миллионах, в базе храним рубли). `quality=2` это «косметический
   ремонт», дефолт самого сайта.

Ссылка в базе и в консоли ведёт на страницу результата с теми же параметрами, её можно открыть
и пересчитать руками. Если Домклик не нашёл дом (обычно адрес новостройки без улицы), в
`domclick_estimates` пишется строка с `error`, и объявление больше не оценивается. Сетевые
сбои строку не создают, попытка повторится на следующем опросе.

## Telegram и доступы

Если задан `CIAN_TELEGRAM_BOT_TOKEN`, каждое новое объявление (с оценкой Домклика и арендой)
уходит всем активным пользователям из таблицы `users`, под ним кнопка «Отслеживать». Нажатие
кладёт пару «чат, объявление» в `watchlist` (повторное снимает), и дальше по этой квартире
приходят изменения цены, снятие с продажи и возвращение, только нажавшему. Кнопка «Скрыть» убирает
квартиру из списков этого пользователя (таблица `hidden`) и снимает слежение, у других она
остаётся. Без токена уведомления выключены, остаётся консоль. Ошибка отправки только логируется.

Любое сообщение боту (`/start`, `/menu`) открывает меню: 🆕 по дате добавления, 💎 по окупаемости
(цена к годовой аренде рядом, есть только у квартир из ленты), ⭐ отслеживаю, 🚫 скрытые. Список
это одно сообщение по 5 квартир со стрелками, номер открывает карточку (Домклик, аренда,
окупаемость, ссылки) с кнопками слежения и скрытия; навигация перерисовывает то же сообщение
(`cian_watch/telegram_screens.py`).

Входящие (нажатия кнопок, команды) бот читает длинным опросом `getUpdates`
(`cian_watch/telegram_bot.py`), это четвёртая задача процесса. Второй экземпляр парсера с тем же
токеном нельзя запускать: Bot API отдаёт апдейты только одному опрашивающему.

Из РФ `api.telegram.org` напрямую не открывается, поэтому Bot API ходит через `CIAN_TELEGRAM_PROXY`:
дома это прокси-хаб gost на gazziiii777 (`http://192.168.31.216:8888`, за ним нероссийский
upstream), и с мака, и из контейнера на сервере адрес один. Мобильный прокси парсера
(`CIAN_PROXY_*`) к Telegram отношения не имеет.

`CIAN_TELEGRAM_CHAT_ID` это владелец: при старте он заводится в `users` сам. Остальным доступ
выдаётся командой, ролей пока нет, все получают одно и то же:

```bash
uv run cian-watch-users add 123456789 "Имя"   # выдать доступ
uv run cian-watch-users remove 123456789      # отозвать, строка остаётся
uv run cian-watch-users list
```

Список получателей читается из базы при каждой отправке, перезапуск не нужен. chat_id
человека узнаётся так: он пишет боту любое сообщение, затем открывается
`https://api.telegram.org/bot<токен>/getUpdates` и берётся `message.chat.id`.

## База и миграции

Postgres 17 поднимается тем же `compose.yaml` в контейнере `cian-watch-db`, данные в именованном
томе `cian-watch-db`. Том переживает `docker compose down`, пересборку образа и обновление кода.
Удаляет данные только `docker compose down -v`.

Схема в `alembic/versions/`. Миграции до `head` парсер накатывает сам при каждом старте
(`cian_watch/db/migrations.py`), поэтому выкатка новой версии не требует отдельного шага.
Новая миграция: `uv run alembic revision -m "что изменилось"`, файл правится руками,
без импорта моделей.

Таблицы:

| Таблица | Что хранит |
|---|---|
| `offers` | продажа и аренда (`deal_type`): id Циана, ссылка, адрес, комнаты, площадь, дом, район, текущая цена (для аренды месячная), дата создания у Циана, когда увидели впервые и в последний раз, статус `active`/`sold`/`rented` и `sold_at` |
| `price_history` | цена объявления на момент `seen_at`; первая строка при появлении, дальше только при изменении |
| `domclick_estimates` | guid и адрес дома у Домклика, рыночная цена, цена метра, диапазон, ссылка на результат, либо `error` |
| `rent_estimates` | медиана, минимум, максимум аренды похожих квартир, размер выборки и охват (дом, 1 км или район) |
| `users` | кто получает уведомления: telegram chat_id, имя, активен ли |
| `watchlist` | кто какое объявление отслеживает (chat_id, offer_id, когда нажал) |
| `hidden` | кто какое объявление скрыл из своих списков |

Посмотреть базу с мака: локальная на `localhost:5433`, серверная через ssh-туннель
`ssh -p 2216 -N -L 5433:127.0.0.1:5433 gazziiii777@77.37.238.72`, дальше любой клиент на
`localhost:5433`, пользователь `cian`, база `cian`, пароль `CIAN_DB_PASSWORD` из `.env`.

Бэкап на сервере: `docker exec cian-watch-db pg_dump -U cian -Fc cian > cian_$(date +%F).dump`,
класть в `/srv/backup/cian-watch/` на диск `sda`. Cron пока не настроен.

Быструю JS-капчу Циана браузер проходит сам. Если капча не прошла или браузер упал
(обрыв прокси, таймаут), браузер перезапускается целиком с новыми отпечатками и пустыми
куками, и попытка повторяется сразу, с паузой `CIAN_RETRY_DELAY_SECONDS` × номер попытки.
Капча или второй сбой подряд означают плохой выходной IP: если задана `CIAN_PROXY_ROTATE_URL`,
перед перезапуском IP прокси меняется (запрос у провайдера занимает около 15 секунд).
После `CIAN_RETRY_ATTEMPTS` неудач подряд парсер ждёт обычный интервал опроса и начинает заново.

## Прокси

Поддерживаются `http://host:port` и `socks5://host:port` с логином и паролем, режим выбирается
по схеме в `CIAN_PROXY_SERVER`.

Мобильный прокси proxys.world пускает только с IP из белого списка, там сейчас только gazziiii777.
Для разработки на маке соединение идёт через ssh-туннель на сервер:

```bash
ssh -N -p 2216 -L 20624:185.234.59.17:20624 gazziiii777@77.37.238.72
```

и в `.env` на маке `CIAN_PROXY_SERVER=socks5://127.0.0.1:20624`. На сервере адрес прокси прямой.

Прокси подключается через локальный форвардер без пароля (`proxy_forwarder.py`): Firefox
внутри Camoufox нестабильно отвечает на 407 от upstream, и навигация зависает.
Внешние сервисы определения IP прокси режет, поэтому `geoip` Camoufox не используется,
таймзона задаётся руками через `CIAN_TIMEZONE_ID`.

Мобильный прокси раз в несколько минут отваливается на минуту-две (ротация IP у оператора):
сначала отказ соединения, потом 502 на любой хост. В логе это `browser failed, restarting it`
с `NS_ERROR_ABORT` / `NS_ERROR_PROXY_BAD_GATEWAY`, браузер перезапускается и опрос продолжается.

## Логи

Каждая строка в stdout это один JSON-объект: `timestamp`, `severity`, `logger`, `message`,
`stream`, поля из `extra`, при исключении `trace`. Порог консоли `CIAN_LOG_LEVEL`.

Если задан `CIAN_GELF_HOST`, те же записи уходят в Graylog по GELF UDP (`cian_watch/logs.py`),
у потока свой порог `CIAN_GELF_LOG_LEVEL` (`OFF` выключает). Каждая запись несёт `stream`
(`cian-parser`, по нему правило стрима в Graylog) и `severity` словом, потому что штатный
`level` в GELF числовой. Оба хендлера работают через очередь в отдельном потоке, чтобы
отправка не тормозила event loop. Нерезолвимый хост отключает поток одной строкой на старте,
а не ошибкой на каждой записи. Graylog дома: с мака `192.168.31.216:12201`; на сервере контейнер
парсера подключён к сети стека Graylog и шлёт в хост `graylog` напрямую (`compose.yaml`), потому
что трафик между docker-сетями одного хоста до опубликованного порта Docker не пропускает.

## Запуск локально

```bash
uv sync
uv run camoufox fetch
cp .env.example .env
docker compose up -d db
uv run cian-watch
```

С окном браузера: `CIAN_HEADLESS=false uv run cian-watch` (или та же строка в `.env`).

## Запуск в Docker

```bash
cp .env.example .env
docker compose up --build
```

Образ сам скачивает Linux-сборку Camoufox и ставит Xvfb. В контейнере нет экрана,
поэтому `CIAN_HEADLESS=false` там не заработает: в образе по умолчанию `virtual`
(окно на виртуальном дисплее, для антибота это лучше, чем `true`). Значение из `.env`
имеет приоритет над дефолтом образа. База поднимается тем же compose, см. раздел выше.

Настройки читаются в таком порядке: переменные окружения, потом `.env`, потом дефолты
из `config/settings.py`.

## Деплой на gazziiii777

Схема из заметки «Деплой через GitHub Actions» в Obsidian: пуш в `main` запускает
`.github/workflows/ci.yml`: ruff и mypy, затем сборка образа `ghcr.io/gazziiii777/cian-watch`
(теги `latest` и `sha-<коммит>`), затем по ssh на сервере `docker compose pull` и `up -d`.
Образ собирается на раннере под amd64, на маке ничего собирать не нужно.

CI видит только код. `compose.yaml` и `.env` лежат на сервере в `~/apps/cian-watch/`,
туда их кладёт `./sync-server.sh` (запускать после правки `.env` или compose, потом
`docker compose up -d` на сервере). Секреты репозитория: `DEPLOY_HOST`, `DEPLOY_PORT`,
`DEPLOY_USER`, `DEPLOY_KEY` (приватный ключ `~/.ssh/eltk_site_gazzi`, его публичная часть
уже на сервере), `DEPLOY_KNOWN_HOSTS` (`ssh-keyscan -p 2216 77.37.238.72`).

Откат: на сервере `echo "IMAGE_TAG=sha-abc1234" >> .env && docker compose up -d`,
вернуться на свежее: убрать строку и повторить. База живёт в томе `cian-watch-db`,
выкатка её не трогает, миграции применяются при старте.
